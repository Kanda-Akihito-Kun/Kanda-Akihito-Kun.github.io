## 探索和猜测

这部分会零零散散地将我从网上搜集来的各种信息，与各种观察到的现象结合起来。

### 1. CDN 节点的命名规律

B 站的 CDN 节点名字几乎可以说是全网范围内可读性最好的了。

结合[录播姬的文档](https://rec.danmuji.org/dev/cdn-info/)和其他开源项目的经验进行总结，节点命名大致有以下四类情况：

<img width="720" src="/images/bilibili-cdn/part-1/01-01-cdn和mcdn.png" />

#### 第一种

```
cn-zjjh-ct-04-05.bilivideo.com
```

这是可读性最好的一种，前面三个参数分别代表 ：[国家、城市、运营商]，并且以 bilivideo.com 结尾。在这个例子中，zjjh = 浙江金华，ct = china telecom。

不过，这里的城市并不一定就是真实的物理地址，至少很多时候解析出来的 IP 所宣告的 GEO 信息和域名中的城市缩写是对不上号的。

根据我的个人经验，教育网节点（fx）可以说是三网体验最好且视频资源最充足的，疑似会主动回源。

另外还有一些特例，比如海外用户可能刷到的：

```
upos-hz-mirrorakam.akamaized.net
cn-hk-eq-01-01.bilivideo.com
```

第一个是杭州 Akamai，据我个人观察，这曾经是很长一段时间内 B 站唯一的面向海外用户的节点；

第二个属于香港系列，是2020年暑假的前后开始出现的，也是目前 B 站仅有的非大陆城市自建节点；

#### 第二种

```
upos-sz-mirrorcos.bilivideo.com
upos-sz-mirrorhwo1.bilivideo.com
```

这种也蛮常见的，除了一眼能看出来的城市名称（sz = 深圳），还有后面紧跟的第三方 IDC 名字（cos = 腾讯云）；

第一种和第二种是最常见的，成分也是最复杂的，其中部分节点也负责冷门资源的兜底。

比如说：

```
d1--ov-gotcha01.bilivideo.com
upos-sz-mirrorcf1ov.bilivideo.com
```

这种名字里面带 “ov”（overseas）的，就是专门负责处理海外流量；

在文章[**点播CDN回源标准化策略**](https://www.bilibili.com/opus/952019023514566692)中提到了“源站UPOS”字眼。实际体验中，南方用户访问上古冷门资源，大概率也会回落到 “upos-sz” 开头的兜底节点，这也是为什么一些开源的视频下载工具首选这类节点；

详细的可以参考这篇帖子：[[关于屏蔽 PCDN 的指引](https://linux.do/t/topic/642419)](https://linux.do/t/topic/642419)，这里面详细分类了部分 B 站的 CDN 类型；

#### 第三种、第四种

```
xy116x196x140x44xy.mcdn.bilivideo.cn:8082
b-baa0a8b36v405flidjs7h5l3dj69b.edge.mountaintoys.cn:4483
```

这种就是社区常说的 “mCDN” 和 “pCDN” 。

与之相关的官方信息几乎没有，只知道前面的前缀是 IP 地址（v4、v6）。现在网上大部分的加速插件都是屏蔽这类地址，因为不少用户反馈这类节点跟抽奖一样，运气不好就会视频加载卡顿。

然后顺带一提，结合[V2EX上的有关讨论](https://www.v2ex.com/t/1112897)，这类节点因为前缀就是 IP 地址，所以在 DNS 解析失败的时候，客户端会直接通过 IP 去访问，所以直接 DNS 屏蔽这类节点效果并不好。更好的解决方案是在 DNS 规则中将所有的此类 host 指向 127.0.0.1，这样才能 fallback 到非边缘节点上。

本人推测过去，是这类边缘节点变动频繁，而传统 DNS 层层下发的时间又很难说，所以才搞出这种直接拼接 IP 地址的操作。

### 2. 客户端获取可用节点列表

这里只说网页端的机制。

在 B 站官方的技术文章[**云厂商CDN故障后，连夜设计了云边端协同新方案**](https://www.bilibili.com/opus/864814003196526630)以及[**B站下行CDN架构的探索与应用**](https://www.bilibili.com/opus/923445482234052759)中有画出资源调度流程图：

<img width="720" src="/images/bilibili-cdn/part-1/01-04-LDNS.png" />

<img width="720" src="/images/bilibili-cdn/part-1/01-02-官方架构图.png" style="zoom: 80%;" />

虽然图一本身是描述 B 站的图片 CDN 架构，但是推测过去基础架构是一样的。可以看出来，客户端是先去和“中心调度服务”交互，然后再去访问集群中的视频资源，没有再看情况回源。

实践中，每次打开视频的时候，客户端都会发起请求，访问一个**初始 html 页面**（https://www.bilibili.com/video/ + 一串视频 BV 号），返回的信息中，会包含每个视频分片的 base_url 和 backup_url，如图：

<img width="720" src="/images/bilibili-cdn/part-1/01-03-调度节点.png" />

虽然不太清楚为什么同时用到了下划线和驼峰，但是在大部分情况下可以认为，base_url 就是第一优先级的 CDN 节点，backup_url 是第二优先级。

只要把这两个地址同时替换成你想要的 CDN 地址，就能实现指哪打哪，和边缘层的 CDN 节点交互并不需要特殊签名机制。当然，指哪打哪的前提是这个节点能拉到对应视频资源，不然就会加载失败。

### 3. 边缘节点的鉴权与回源，及部分冷门视频拉取失败

在上述的 html 初始页面中，每个分片的请求地址都会带有一串签名参数（UPSIG），推测过去这串签名的入参中并不包含 host 信息。因为拿着这串签名参数直接去请求任意边缘节点，都不会因为签名原因而报错（实测一旦修改签名的一个字符就会报错），这也是各种开源工具能够实现切换 CDN 节点的基础前置条件。

在文章[**点播CDN回源标准化策略**](https://www.bilibili.com/opus/952019023514566692)中有提到：“厂商CDN回源时额外新增OSIG签名，隔离CDN和源站的鉴权逻辑”。所以正常情况下，，客户端直接去拉源站拉视频是不可能的，只能和边缘节点斗智斗勇。

接着，文章又提到了“异步回源”的概念，文章插图：

<img width="720" src="/images/bilibili-cdn/part-1/01-05-异步回源.png" />

再结合文章[**B站下行CDN架构的探索与应用**](https://www.bilibili.com/opus/923445482234052759)，其中提到的“预热系统”。或许这就是为什么实际观察下来，有一些节点明明一个小时前还没有对应的视频资源，只能 fallback，但是过了一个小时却莫名其妙有资源的原因。

### 4. 特殊请求参数

<img width="720" src="/images/bilibili-cdn/part-1/01-06-特殊参数.png" />

还是上述提到的初始页面，里面带有两个特殊参数：[os、og]。暂时不知道这两个参数具体是何意味，推测过去，os = object source，og = object group。

目前暂时没发现这两个参数有什么特殊作用，但是推测过去**可能和回源配置有关**。本人一开始猜想，修改这里的参数是否能强制触发同步回源，所以尝试过手动将其替换为 cos 或者 bcache，结果似乎并不影响结果？

能找到的开源信息只有在 [替换 PCDN 功能建议](https://github.com/SukkaW/Make-Bilibili-Great-Than-Ever-Before/issues/16) 这个 issue，提交者建议 “不必让用户选择用哪个 Host 替换，直接按播放链接的 og 参数来就行”。

### 5. 从 BGP 层面发散出来的联想

我在前文有提过，说部分城市的节点解析出来的 IP，其 GEO 宣告信息和节点的城市缩写相差甚远。我的第一反应是被 DNS 层级的负载均衡或者某些上游 BGP 规则给拐走了。如果是这样，直接指定对应城市的自建节点这一行为会直接变得毫无意义。

但是这种情况应该不至于，因为我拜读了官方的文章：[**B站下行CDN架构的探索与应用**](https://www.bilibili.com/opus/923445482234052759)，[**B站公网架构实践及演进**](https://www.bilibili.com/opus/740129406252482739)，以及[**视频 CDN 融合资源的调度策略探索落地**](https://www.bilibili.com/opus/1025864968860336129)，再结合前面提到的视频预热的文章。

可以看出来，B 站为了灵活、及时、可控、削峰，已经是尽可能把所有的调度都塞在应用层了。甚至是在四层负载均衡这块，也搞出了 [**B站边缘网络四层负载均衡器的探索与应用**](https://www.bilibili.com/opus/872606787572858983) 这种直接在业务端边车处理四层流量的操作。

外加 B 站很早开始就大量使用 QUIC 和 WebRTC，所以应该是不可能接受路由乱飞的情况。

### 6. 独立的签名体系

可能 B 站老用户都知道，看港澳台专属的番剧的时候，只要一开始加载页面的时候挂着梯子就行，后续断开梯子也能正常观看，这时候连上的节点有不小概率是**杭州 Akamai**。

然而直接使用国内的网络环境去请求初始化 html 页面，用其中的参数去请求杭州 Akamai 节点，是无论如何都拉不到视频的，貌似签名体系不是一套。

## 收尾

原本是打算只写一篇文章的，大致囊括了[观察现象、官方技术信息收集、还原架构、横向对比、CCB脚本实践和问题]这几个小点，结果发现越写越多，一篇根本写不完，所以就分个几期慢慢写了。

以及，我不是 B 站的员工，也没有参加过大型 CDN 的架构设计，所以只能根据公开信息瞎猜。

文章中引用了大量的官方技术博客、专利、开源项目，这些都是非常优质的项目！
感谢在 B 站工作的老师们，主动分享大量高质量的技术文章，也对开源社区给予了一定的包容。
